# Промт для разработки приложения «Журнал репетитора»

> Скопируйте всё, что ниже разделительной линии, в новую сессию Claude (Cowork),
> предварительно подключив папку проекта. Рядом должны лежать `DESIGN.md`
> (дизайн-документ) и `prototype.html` (рабочий прототип) — промт ссылается на оба.

---

## ЗАДАЧА

Реализуй настольное приложение «Журнал репетитора» по дизайн-документу `DESIGN.md`,
лежащему в этой папке. **Прочитай `DESIGN.md` целиком перед началом работы** — он
содержит модель данных, схему БД, описание интерфейса и логику расчётов. Этот
промт задаёт технические требования и порядок работы; при расхождениях
`DESIGN.md` главнее в вопросах поведения продукта, промт — в вопросах реализации.

Рядом лежит `prototype.html` — работающий одностраничный прототип, согласованный
с заказчиком. **Открой его и разберись, как он устроен, до того как писать код.**
Он задаёт эталон поведения и внешнего вида: сетка, статусы ячеек, карточка
ученика, форма оплаты, журнал изменений, палитра и плотность вёрстки. Логику
расчётов (`calc`), механизм операций (`apply` / `commit` / `undo` / `revertEntry`)
и набор статусов переноси один в один — они уже покрыты тестами. Что нужно
сделать лучше прототипа: хранение в SQLite вместо localStorage, миграции,
резервные копии, сборка установщиков.

## КОНТЕКСТ ЗАКАЗЧИКА

Репетитор английского языка. Ведёт 15–30 учеников. Каждый ученик покупает пакет
уроков (обычно 8 или 10), платит в рублях или долларах по своей цене. Сейчас
учёт в электронной таблице: строки — ученики, столбцы — календарные дни, зелёная
заливка = занятие прошло. Приложение должно заменить эту таблицу, сохранив её
главное свойство — **все ученики и весь месяц видны на одном экране** — и
автоматизировать подсчёт баланса уроков и денег.

Пользователь не программист. Приложение должно ставиться из установщика, иметь
ярлык и запускаться двойным кликом на Windows и на macOS.

## СТЕК (обязателен)

- **Tauri 2** — оболочка, установщики, ярлыки
- **React 18 + TypeScript + Vite** — интерфейс
- **Tailwind CSS** — стили
- **Zustand** — состояние
- **SQLite** через `@tauri-apps/plugin-sql` — хранилище
- **Vitest** — тесты доменной логики

Не подключай сторонние UI-библиотеки компонентов и не добавляй серверную часть,
авторизацию, аналитику или любые сетевые вызовы. Приложение работает полностью
офлайн.

## ЧТО КРИТИЧНО ВАЖНО

1. **Баланс вычисляется, а не хранится.** Никаких полей вида `lessons_left`,
   которые кто-то инкрементирует. Баланс — всегда чистая функция от списка
   пакетов и списка занятий. Это исключает рассинхронизацию и делает отмену
   любого действия тривиальной.

2. **FIFO-привязка уроков к пакетам.** Считается на лету. Именно она даёт
   корректный ответ на «сколько осталось из текущего пакета», когда новый пакет
   куплен до того, как закончился предыдущий. Алгоритм — раздел 7 `DESIGN.md`.

3. **Единый механизм изменений** (раздел 5 `DESIGN.md`). Ни одна мутация данных
   не делается «мимо» функции `apply/commit`: иначе изменение не попадёт ни в
   отмену, ни в журнал. Это архитектурное правило, а не пожелание — проверь его
   тестом, который считает записи журнала после каждого типа действия.

4. **Журнал изменений только на добавление.** Откат не стирает историю, а
   дописывает в неё запись «Откат: …». Никаких `UPDATE` и `DELETE` по
   `audit_log`, кроме плановой очистки записей старше года.

5. **Автосохранение без кнопки «Сохранить».** Запись в базу — сразу после
   изменения, с небольшой задержкой для серии кликов; состояние видно в подвале.

6. **Отметка занятия — один клик, без подтверждений и модальных окон.** Это
   действие выполняется сотни раз в месяц. Всё остальное может быть в меню.

7. **Данные пользователя неприкосновенны.** Любая операция, удаляющая историю,
   требует явного подтверждения. Миграции схемы БД делают резервную копию перед
   применением.

8. **Валюты не смешиваются и не конвертируются.** Итоги всегда раздельные:
   «42 000 ₽ · 360 $».

9. **Никаких системных `alert` / `confirm` / `prompt`.** Только свои диалоги —
   они и выглядят лучше, и поддаются автотестам.

## ПОРЯДОК РАБОТЫ

Иди этапами из раздела 9 `DESIGN.md`. После каждого этапа приложение должно
запускаться и быть работоспособным — никаких «соберём всё и проверим в конце».

**Этапы 2 и 3 (доменная логика и механизм операций) сделай до интерфейса и
покрой тестами.** Файл `src/domain/balance.ts` — ядро приложения; ошибка в нём
испортит все цифры. Обязательные тест-кейсы:

- пакет 8 уроков, 3 проведено → баланс 5, «5 из 8»
- два пакета (8 + 10), проведено 11 → баланс 7, «7 из 10», первый пакет закрыт
- проведено 10, куплено 8 → баланс −2, долг 2
- отмена вовремя не уменьшает баланс, отмена поздно и неявка — уменьшают
- перенос не списывает урок дважды (списывается только фактическое занятие)
- снятие отметки возвращает урок в баланс
- флаг `consumes = 0` на занятии со статусом `held` не списывает урок
- ученик без пакетов, но с проведёнными занятиями → баланс отрицательный, приложение не падает
- пакет с нулём уроков / занятие без пакетов → без исключений
- повторная установка того же статуса не создаёт вторую запись в ячейке

Для механизма операций (этап 3):

- `apply` возвращает обратную операцию, применение которой восстанавливает состояние
- undo → redo → undo возвращает данные ровно в исходное состояние
- откат записи из середины журнала снимает только её, не трогая более поздние
- каждый тип действия (занятие, оплата, карточка, архив) даёт ровно одну запись журнала
- undo сам создаёт запись журнала, а не удаляет существующую

**Этап 4 (сетка) — самая ответственная часть интерфейса.** Требования:

- левая панель (имя, индикатор, остаток, цена) зафиксирована при горизонтальной
  прокрутке; шапка с датами зафиксирована при вертикальной
- сегодняшняя колонка подсвечена, выходные затонированы
- строка 36 px, колонка дня 34 px — месяц на 25 учеников без прокрутки на
  ноутбучном экране
- клик по ячейке переключает «пусто ↔ проведено» с мгновенной реакцией
  (оптимистичное обновление, запись в БД — следом)
- правый клик открывает меню статусов; на macOS учти также Ctrl+клик
- у каждого статуса свой символ, а не только цвет (✓ ○ ✕ →) — читается при
  дальтонизме и при печати
- чередование строк, подсветка строки под курсором, отделённые линией
  понедельники, приглушённые будущие даты

## ТЕСТОВЫЕ ДАННЫЕ

Сделай команду `npm run seed`, наполняющую базу правдоподобными данными:
8 учеников (5 в рублях, 3 в долларах), у каждого 1–4 пакета за последние
3 месяца, занятия 1–2 раза в неделю, и обязательно среди них — ученик с балансом 1,
ученик с балансом 0, ученик с долгом, ученик с двумя активными пакетами и
ученик с переносом. Плюс полтора десятка записей в журнале изменений с
правдоподобным временем — иначе панель истории на демонстрации будет пустой.
Готовый генератор с подбором нужных балансов есть в `prototype.html`
(функция `seed`) — можно перенести логику оттуда.

Это нужно, чтобы все состояния интерфейса можно было увидеть сразу, не набивая
данные руками.

## ГРАФИКИ — ПРАВИЛА, КОТОРЫЕ НЕЛЬЗЯ НАРУШАТЬ

- **Никогда не совмещай две шкалы на одной оси.** Рубли, доллары и часы —
  три отдельных графика, а не один с двумя осями. Это первая по частоте ошибка
  в дашбордах и самый быстрый способ соврать читателю.
- Один ряд на графике → легенда не нужна, её роль играет заголовок.
- Подписи значений только у последнего и наибольшего столбца, не у каждого.
- Столбец не толще 24 px, скругление 4 px только сверху (у края данных),
  основание прямое, растёт от единой базовой линии.
- Сетка — сплошная линия в 1 px цветом на шаг от фона, никаких пунктиров.
- Текст никогда не красится в цвет ряда — только в цвета текста.
- Под каждым блоком графиков — таблица с теми же числами (и как доступная
  альтернатива, и для сверки).
- Палитра графиков уже подобрана и проверена, бери её из прототипа:
  светлая тема `#2a78d6` / `#eb6834` / `#1baf7a`, тёмная `#3987e5` / `#d95926` / `#199e70`.
  Если будешь менять — проверяй на различимость при дальтонизме, а не на глаз.
